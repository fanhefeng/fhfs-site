# 后台编辑与备份保护

`fhfs` 与 `fhfs-site` 的后台独立部署，内容共用 Neon。定时公开快照、私有备份和 Healthchecks.io 巡检仍由 `fhfs-site` 负责；两个后台使用相同的写入协议。

## 正常编辑

每次已鉴权的内容写入都通过 `src/app/admin/backup.ts`：

1. 在一个 Read Committed 事务中锁定对应内容表，公开页面读取不受阻。
2. 核对实际总行数、公开行数与 `admin_content_state` 的预期值。缺少记录或数量不符时停止写入，避免下一次编辑掩盖此前的数据丢失。
3. 执行原有新增、保存、删除或整表替换；有上传的内容仍保留原有租约 CTE。
4. 记录修改后的总行数、公开行数与操作标识，一起提交。任何一步失败均回滚。

主动删除最后一条、清空列表、把最后一篇公开内容改为草稿，都会记录合法的公开行数 0。无需人工修改快照或关闭告警。

公开导出使用一个只读 Repeatable Read 事务读取全部内容和预期行数，避免编辑恰好发生在导出中途造成误判。只导出公开内容；`evidence.json` 只保存公开行数，不公开草稿数量、操作日志、凭据或审计表原始数据。

## 异常保护

- 没有对应后台事务的归零或部分行数丢失，均会因数量不符拒绝备份。
- 错误数据库、证据缺失、遗漏导出表、损坏的数量、缺少公开上传租约，均拒绝备份。
- 定时备份只有读取审计表的权限，不能自行重置预期值。
- 历史快照仍保留在 `db-snapshots` 的 Git 历史中；私有完整备份仍独立执行。
- 这里保护数量异常，不能识别有数据库写权限的人同时篡改内容和审计表，也不把行数相同的内容损坏当成已检测到。

## 一次性上线

共享 schema 由 `fhfs-site` 管理，仅在那里新增 `drizzle/0018_admin_content_state.sql`。既有内容表和上传协议不变。

生产迁移需要遵守仓库关于迁移的明确授权约束。上线前先完成两个项目的 check、build 和只读公开页面验证，再：

1. 确认只有 0018 待执行；新增审计表，为现有 `ci_readonly` 角色仅授予 SELECT。
2. 取最新、经过核对的 `db-snapshots/backup/db.json`，运行 `scripts/backup-state-init.mts <已核对的 db.json>`。该工具锁定内容表并要求每张表的公开行数与核对过的快照完全相同，才初始化元数据；既有审计记录不覆盖，内容不修改。
3. 发布两个后台。旧版本不记录编辑证据，滚动发布期间应避免编辑；旧客户端的未记录数量变化会被新版本拦截。
4. 创建一份包含新增审计表的私有备份，并在已隔离、有保护标记的恢复数据库完成恢复演练，更新巡检的 schema 证据。
5. 执行新的公开快照，确认导出、保护检查、提交均成功，随后核对自动巡检和 Healthchecks.io 的真实成功信号。

受控恢复、导入或直接 SQL 修改也属于后台之外的操作。执行前需明确评审并规划证据同步，不能把初始化工具加入定时任务来消除告警。
